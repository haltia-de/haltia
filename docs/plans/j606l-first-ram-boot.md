# TB-J606L: первая ограниченная RAM-загрузка Linux

25 октября 2026. Проект сценария для задач устройства
[№ 5](https://github.com/haltia-de/device-lenovo-tb-j606l/issues/5) и
[№ 6](https://github.com/haltia-de/device-lenovo-tb-j606l/issues/6).
Контроллер реализован и проверен для ограниченных проб. Результаты R1 и
R3 приведены ниже; работоспособный Linux и завершённый dual boot не доказаны.

## Проверяемый результат

Один запуск нового ядра J606L в RAM, полный проверенный USB-кадр с ранним
журналом, затем подтверждённый возврат прежнего Android B. Это первый этап
dual boot; постоянного Linux rootfs, Phosh/phoc и ежедневной эксплуатации
эта проба не подтверждает.

Исходная точка: Android B работает, критичные разделы и обе GPT шести
экспонированных UFS LUN прочитаны двумя проходами, полные хэши совпали,
независимая проверка и копия на другом физическом диске завершены.
Ограниченный проход Android → fastboot → Android B уже выполнен успешно.
Размеры всех 17 критичных разделов fastboot совпали с резервами.
Подробности — в [профиле экземпляра](../research/2026-10-24-j606l-stock-profile.md).

## Выбранный маршрут для реализации контроллера

Первый кандидат — downloaded boot при выбранном A, с невалидным DTBO
только A. Новый boot не записывается в раздел. Android B сохраняет свои
boot, DTBO, vbmeta, recovery и данные. Переключение active slot штатно
меняет A/B metadata; неизменность всей GPT после этого не заявляется.
В reference выбор слота также переключает partition-slot/GUID mapping
и UFS boot LUN. Отсутствие TZ/Keymaster/rollback побочных эффектов
не утверждается; новых rollback indices в наш образ не добавлено.

Причина подготовки DTBO A: в Qualcomm/SHIFT reference downloaded boot
всё равно получает активный DTBO, а CmdBoot вызывает ClearUnbootable для
активного слота. Поэтому проба при активном B не выбрана. Одного board-id
34/3 недостаточно для доказательства обхода overlay: CheckAllBitsSet
также учитывает PMIC, foundry, subtype и SKU; необходимых PMIC properties
в новом DTB нет. При невалидном DTBO reference использует full/appended
DTB, включая fallback для единственного DTB в образе v2.

Это обоснование кандидата по reference другого производителя. Работу
конкретного Lenovo ABL устанавливает только ограниченная проба. Если
Lenovo откажет, автоматически менять vbmeta, recovery, заголовок или
повторять boot нельзя. Recovery A в данном кандидате не изменяется.

## Замороженные входы

### Новая ограниченная проба R3, 25 октября

Первая проба R1 не дала Linux proof; Android B впоследствии восстановлен
и проверен. Для отдельно разрешённой пользователем одной пробы R3 таблица
ниже заменяется новым RAM-образом: 2129920 байт, SHA256
`a5ce4a6e8de90989498e328f9e1ea623c7eae448a418eebb0629b09c4728c733`,
build `haltia-j606l-95b9bdba96ce1be5`, release
`7.1.0-haltia-j606l-ramdiag-03`. Manifest исходников имеет SHA256
`7ee7740cd02513e1623c259b2c49214ddaff67ac8da6dcd8294f8a2f53a03da4`.

Независимая чистая сборка дала побайтово тот же образ; прошли 18 тестов,
C/PTY-проверки, аудит DTB/USB/CPIO/заголовка и проверка relocation реального
ELF. R2 без relocation отвергнут отрицательным контролем. R3 включает
RELOCATABLE=y при RANDOMIZE_BASE=n; проверены смещения 0 и 0x80000.
Физический адрес загрузки Lenovo и причина отказа R1 остаются неизвестны;
эти проверки не доказывают аппаратную загрузку R3.

Маршрут и ограничения этого документа сохраняются. Для R3 требуются
отдельная замороженная копия контроллера и reader с новой привязкой
образа/build, свежая идентификация устройства и новое одноразовое
приватное разрешение. Все прежние разрешения остаются использованными.
Резервы DTBO A и нулевой DTBO не меняются. Повтор boot и запись payload B
не разрешены; подтверждённый возврат B остаётся обязательным результатом.

Проба R3 выполнена один раз 25 октября. Отдельный контроллер с SHA256
`f060fea220e6518ffaddf8a7d926d916399736569c44979db4ff9858435347d8`
прошёл независимые 42 теста и проверку входов; перед запуском повторно
проверены 116 файлов резервов на двух физических дисках. Новое одноразовое
разрешение использовано; повторного RAM boot не было.

Итог R3: Linux proof отсутствует, захвачено 0 байт; наблюдатель зафиксировал
возврат bootloader. Контроллер выбрал B и перезагрузил устройство; исходные
модель, сборка, слот `_b` и boot_completed=1 подтверждены дважды. Независимая
проверка всех 188 командных записей подтвердила завершение клиентов без
таймаутов/переполнения, один flash `dtbo_a`, один RAM boot и отсутствие
записи payload B. Общая блокировка освобождена, контроллер завершён.
Причина отсутствия Linux USB остаётся неизвестной. Следующий шаг — офлайн
разбор boot ACK и временной последовательности USB, затем подготовка
обоснованного кандидата; повтор R3 этим результатом не разрешён.

запуск. Старое разрешение на preflight не подходит. Приватные пути,
serial и логи в публичный репозиторий не попадают.

## Последовательность одного запуска

1. Взять общую блокировку планшета и удерживать её до остановки всех
   собственных процессов и завершения проверки B. Проверить неизменность
   входов и принятых резервов, доступную вторую копию. Подтвердить точные
   модель, сборку, слот B и boot_completed=1. Чужие USB-контроллеры
   блокируют запуск; штатный уже работающий ADB-сервер не перезапускается.
2. Один переход в bootloader. Требовать свежую USB-enumeration на прежнем
   порту, независимое совпадение serial, is-userspace=false, unlocked=true,
   current-slot B, B successful=true/unbootable=false. Сверить размеры
   boot A/B и DTBO A/B с резервами; max-download-size должен однозначно
   вмещать образ. Неподдерживаемые ответы остаются unknown и не заменяются
   предположениями. Ошибка до записи завершает пробу возвратом в B.
3. Разрешённая запись — только явно названный `dtbo_a` и только указанный
   нулевой файл. Fastboot может подготовить весь целевой раздел; это не
   обещание изменить физически лишь первые 4096 байт. Полный исходный
   DTBO A уже сохранён. Другие разделы не передаются команде flash.
4. Выбрать A и свежим чтением подтвердить current-slot A. Штатно
   перезагружаться в A нельзя: boot A не заменяется этим сценарием.
5. Подготовить ограниченный наблюдатель с точной привязкой к новому build
   ID и USB-порту. Один downloaded boot указанного RAM-образа. Контроллер
   должен учитывать, что передача могла завершиться даже при потере ACK:
   такой результат не разрешает повторный boot.
6. Наблюдать не более 120 секунд, не более 4 MiB приватного захвата.
   Успех требует согласованных build ID/release/aarch64/PID1/RAM rootfs
   и полного kmsg-кадра с правильными длиной, CRC и ранней строкой версии
   ядра. Само появление ACM или три строки без журнала недостаточны.
   PID1 работает не дольше 90 секунд и один раз запрашивает bootloader.
7. Остановить и подтвердить завершение всех собственных читателей и
   команд. Только затем работать с вернувшимся fastboot: проверить свежую
   привязку, выбрать B, повторно прочитать current-slot B и выполнить один
   обычный reboot. Дважды подтвердить исходные модель, сборку, слот B и
   boot_completed=1. Итоги Linux proof и возврата B хранить отдельно:
   работающий B не доказывает загрузку Linux.

В reference set_active сбрасывает successful выбранного слота. Поэтому
successful=false сразу после выбора B допустим: до reboot проверяются
current-slot B, unbootable=false и положительный retry, а итогом служит
реально завершившаяся загрузка Android B. Если непродолжимая ошибка VB2
сама вернула рабочий Android B, контроллер подтверждает этот результат
без повторного Linux boot и без лишнего переключения слота.

Каждая команда имеет deadline, отдельные ограниченные stdout/stderr и
подтверждённый process-group cleanup. rc=0 недостаточен: на этом fastboot
ответ FAILED уже встречался при rc=0. Для изменяющих состояние команд
нужны ожидаемые protocol ACK и независимые проверки состояния; FAILED
всегда является отказом. Повтор команды после неоднозначного ACK запрещён.

## Остановка и состояние A после пробы

При identity mismatch, неизвестном режиме/слоте, неостановленном
контроллере или неожиданной USB-enumeration новых изменяющих команд нет.
Если точный fastboot доступен и собственные клиенты остановлены, возврат
выбором B остаётся отдельной разрешённой ветвью восстановления. При
недоступном fastboot контроллер останавливается и сообщает root; физическое
восстановление координируется с человеком, без циклов boot/reset.

Если ядро зависнет до PID1, panic=0 не вернёт B автоматически. Нажатие
питания, проверенное ранее в EDL при активном B, не считается универсальным
восстановлением из Linux при активном A.

После выполненной записи DTBO A остаётся зарезервированным для Linux
и не считается штатным Android A. Автоматического восстановления DTBO A
и необоснованного утверждения о readback нет. По завершении B должен быть
активен; обычная загрузка A допустима только после отдельной подготовки
известного постоянного Linux boot/rootfs либо проверенного восстановления.
До этого эта проба не считается завершённым dual boot.

## Что проверить до аппаратного запуска

Контроллер и его fixtures должны покрывать ошибки каждой фазы, отказ ACK
при rc=0, потерю USB, неверные serial/slot, исключения при сохранении логов,
таймауты, завершение читателя до возврата B и запрет повторного boot.
Сначала проверяется точный код и замораживаются хэши, затем root разрешает
один конкретный запуск. Произвольного интерактивного flash/reboot нет.
