# Открытые оркестраторы агентов: годятся ли Haltia (21 октября 2026)

Второй обзор за день. Первый (утром) сравнивал по описаниям; этот — по
требованиям, которые сложились после ADR 0005–0010, и по документации и коду
кандидатов.

## Наши требования

1. Задачи — Issue в 17 репозиториях организации, запуск по метке
   (`agent:ready`), модель — по метке `model:*`.
2. Исполнители — CLI по подписке: Claude Code, Codex, Grok. Без ключей API.
3. Работа на ПК сборки, не в облаке; таймер systemd.
4. Исполнитель не получает git и GitHub: коммит, пуш, PR и метки делает
   оркестратор (ADR 0006).
5. Песочница: пустой домашний каталог, скрытые ключи подписи и сокеты,
   свои пространства имён; сеть — только поиск документации (ADR 0010).
6. Не больше двух одновременно и одного на репозиторий; лимит подписки —
   `agent:blocked` без смены модели.
7. Ревью по иерархии моделей (ADR 0008), слияние по правилам ADR 0009,
   выпуск только с одобрения человека.
8. Задачи с планшетом — живым сеансам; живые сеансы в herdr (ADR 0007).

## Выводы

- **Ни один не закрывает требования 4 и 5 из коробки.** Sortie ближе всех по
  модели (метки, много репозиториев, локальные CLI, git в крючках
  оркестратора), но песочницу прямо не берёт на себя, а адаптер Claude
  принимает только режим обхода подтверждений. Чтобы взять Sortie, пришлось
  бы заново сделать то, что уже сделано: обёртку bwrap через `agent.command`,
  копию без `.git` (его рабочая папка — обычный клон, и крючки git после
  агента — та же дыра, что закрыта в ADR 0006), иерархию ревью, правила
  слияния, `needs:tablet`.
- **gh-aw** ближе всех по безопасности: агент только читает, записи
  делают отдельные задания, сеть через файрвол с белым списком, токены у
  прокси. Но он работает в Actions и требует ключи API: это оплата за
  токены, а ADR 0005 строится на подписках. Как образец — полезен.
- **Настольные** (Orchestrator.inc, Vibe Kanban, Claude Squad) — для
  человека за экраном, без запуска по Issue; у нас эту роль играет herdr.
- **baton, Symphony** — узкие или только спецификация.

## Рекомендация

Оставить свой диспетчер: около 600 строк без зависимостей, точно под наши
ADR. Взять идеи:

1. **Из Sortie:**
   - обратная связь после PR: падение CI и замечания ревью возвращаются
     исполнителю как продолжение задачи;
   - самопроверка исполнителя перед «done»;
   - сигнал «менять нечего» как законный итог, не ошибка;
   - отказ на вопросы агента, на которые может ответить только человек;
   - сверка состояния после перезапуска;
   - `--dry-run` и `validate` конфигурации.
2. **Из gh-aw:**
   - шаг проверки diff на угрозы между исполнителем и пушем (секреты,
     изменения `.github/workflows`, бинарники);
   - сеть исполнителя через прокси с белым списком доменов вместо
     полного выхода.

Вернуться к Sortie стоит, если понадобится обратная связь CI и
авто-слияние в большом объёме: тогда сравнить стоимость доработки своего
диспетчера с обёрткой Sortie нашей песочницей.

## Sortie подробно: что настраивается (по коду v1.29.0 и `docs/`)

Сам проект: Go, Apache-2.0, около 440 тыс. строк с тестами, 30 ADR и
спецификация на 29 разделов, выпуски каждые 2–3 дня. Один файл
`WORKFLOW.md`: YAML сверху (настройки), Markdown снизу (шаблон задания на Go
templates). Настройки перечитываются на ходу.

### Что можно подогнать под нас

| Наше правило | Как в Sortie |
|---|---|
| Метки `agent:*` | Состояния задачи — метки: `active_states`, `in_progress_state`, `handoff_state` (у нас `agent:review`), `terminal_states`; `query_filter` сужает выборку (`label:agent:ready`). Метки он не создаёт, ждёт готовые. |
| Модель по метке `model:*` | `dispatch.rules` с `match.labels` или `stage`: правило выбирает вид агента, шаблон и модель. |
| Ревью по иерархии (ADR 0008) | Цепочки стадий: правило с `next` после успеха ставит метку следующей стадии; стадия «ревью» может идти на другой модели и своём шаблоне. Плюс `self_review` с командами проверки и вердиктом агента. |
| Исполнитель без git (ADR 0006) | Sortie сам git не делает вовсе: клон, ветка, коммит, пуш и PR — в крючках `after_create`, `before_run`, `after_run`, которые запускает оркестратор вне агента. Значит, нашу схему «копия без `.git`, коммит в своём клоне» можно написать крючками. |
| Песочница bwrap (ADR 0010) | `agent.command` — вектор аргументов; адаптер дописывает свои флаги. Обёртка `haltia-sandbox claude …` встаёт без правок Sortie. |
| Файл статуса исполнителя | Есть свой: `.sortie/status` (`blocked`, `needs-human-review`, `no-change-needed` с причиной). |
| Лимит подписки | Повторы с экспоненциальной паузой; учёт денег в долларах (для подписок бесполезен). Метки `agent:blocked` при лимите и запрета смены модели нет — это пришлось бы делать крючком. |
| Не больше двух | `max_concurrent_agents`, по состояниям — `max_concurrent_agents_by_state`. |
| Обратная связь | Реакции: падение CI, замечания ревью людей и ботов, конфликты слияния — идут агенту продолжением; авто-слияние с воротами; команды-метки на PR (`label-review`, `label-fix`). |
| Планшет | Нет. `needs:tablet` — исключить в `query_filter`. |

### Что не подходит

1. **Один репозиторий на экземпляр.** GitHub-трекер ищет
   `repo:<owner>/<repo>` (код `internal/scm/github/tracker.go`). На 17
   репозиториев — 17 процессов со своими базой, портом и лимитом
   параллельности: общего «не больше двух на ПК» нет.
2. **Claude только в режиме обхода подтверждений.** Предпроверка
   пропускает лишь `bypassPermissions`; `allowed_tools`/`disallowed_tools`
   передаются, но shell у агента по умолчанию есть. В нашей песочнице это
   терпимо, но правило ADR 0006 «у Claude нет Bash» пришлось бы держать
   через `disallowed_tools`.
3. **Агенту дают инструменты оркестратора** через свой MCP-сервер:
   `tracker_api` ходит в трекер с токеном Sortie, ревью по метке ждёт, что
   агент сам возьмёт diff и оставит комментарии «своими средствами SCM».
   У нас у исполнителя нет ни токена, ни GitHub — эти инструменты пришлось
   бы запрещать.
4. **Рабочая папка — обычный клон и переиспользуется** между запусками.
   Песочница не цель проекта (раздел «Goals and Non-Goals»), раздел о
   безопасности перекладывает её на развёртывание.
5. **Codex идёт через `codex app-server`**, который сам записывает папку в
   доверенные в настройках пользователя (так в их заметках к адаптеру) —
   с нашей песочницей и пустым домом это безвредно, без неё — нет.
6. Grok — только через общий адаптер ACP; что `grok agent stdio` говорит на
   ACP, не проверено.

### Итог по Sortie

Подогнать можно почти всё, но ценой: 17 экземпляров, обёртка-песочница,
крючки с нашей логикой копии и коммита, запрет его инструментов для агента,
отдельный счётчик лимитов подписки. По сути остаётся наш код в крючках плюс
чужой демон на 440 тыс. строк. Выигрыш — реакции на CI и ревью, панель,
повторы, стадии. Брать стоит идеи (реакции, стадии, самопроверку,
`no-change-needed`), а не сам Sortie — пока у нас 17 репозиториев и общий
лимит на ПК.

### Выводы из поиска

- Ни один проект не даёт из коробки одновременно: опрос Issue по многим
  репозиториям, Claude Code + Codex + Grok по подписке, исполнителя без
  git и GitHub и песочницу. Подтверждённой поддержки Grok CLI в проектах с
  опросом Issue нет.
- По **процессу** ближе всех Orbi: метка, таймер systemd, агент до
  коммита, пуш раннером, независимое ревью другой моделью, слияние только
  проверенной головы, выпуск только по метке. Это лучший образец для наших
  состояний ревью, слияния и выпуска. Взять сам нельзя: только оболочка Pi,
  один репозиторий, учётные данные в окружении агента, AGPL.
- По **границе учётных данных** ближе всех codex-orchestrator: та же идея,
  что ADR 0006, но только для Codex и без пользователей.
- У no_human стоит перенять сторож против ослабления тестов и
  состязательное ревью; у Cyrus — прокси исходящих с белым списком.

Рекомендация не меняется: свой диспетчер, идеи — из Sortie (реакции на CI и
ревью, стадии, `no-change-needed`), Orbi (ревью до проверенной головы,
ворота человека), gh-aw и Cyrus (проверка diff и прокси исходящих),
no_human (сторож тестов).
